## Critical / Blocking

### Pre-Public-Launch (must fix before non-pilot users)
- [ ] **ADR-052 access expiry is NOT an authorization boundary — the renderer can run arbitrary Cypher** -- Review of the (already-shipped) v0.0.34 access-expiry work, 2026-08-07. `window.lite.neon.query()` is exposed on every window using `preload-lite`, and `validateCypher` (`lite/neon/main.ts`) checks only that the string is non-empty — no read-only restriction, no statement allowlist. So any renderer-side code can run `MATCH (a:Asset)-[:BELONGS_TO]->(s:Space {id:'<restricted>'}) RETURN a` to read a Space it has no grant to, or `MATCH ()-[r:HAS_ACCESS]->(:Space {id:...}) SET r.expiresUnixMs = null` to make every grant permanent. Every `GRANT_LIVE` / `SPACE_VISIBLE` / `ASSET_VISIBLE` predicate only constrains queries THIS client chooses to send; it constrains nothing about what the account's credentials can do. Compounding it, `ADD_SPACE_MEMBER` performs NO authorization check on the caller (`$viewerId` is not referenced), so even without the Cypher channel an expired member can call `members.add(space, self, {expiresAt:null})` and restore permanent access. Verified by reading both code paths. Decision needed: either the expiry/visibility rules move server-side (Edison-enforced), or they are documented as UI-level organization rather than security. Until then no visibility claim in the product copy should read as a security guarantee. Related: the baked-in Neon credentials blocker below — same root (the client holds full graph authority).
- [ ] **createBinary ambiguous-failure cleanup can destroy landed assets; Files delete-by-key never works** -- caught live 2026-08-06 during the video-tile drive: `items-createBinary` uploaded the mp4, the graph CREATE reported failure (likely Neon HTTP timeout) *while the write actually landed*, so the orphan-cleanup path tried to DELETE the just-uploaded bytes of a node that exists. The only reason the asset survived is the second bug: `files.delete` by key fails with `Could not find any entity of type "FileItem"` (the service wants a fileId / differently-composed identifier), so cleanup deletes nothing -- which also means genuinely orphaned uploads are never reclaimed. Fix both: (1) on create failure, verify the node is truly absent (re-read by id) before deleting bytes, or delete graph-first; (2) resolve the FileItem lookup the delete API actually requires. Evidence: logs 15:35:18-21Z (`createBinary: orphan cleanup failed`, `files.delete.fail FILES_NETWORK`). UPDATE 2026-08-06: root cause confirmed as Edison Neon READ-AFTER-WRITE inconsistency (a transcript create hit the same "disappeared after creation" while the node existed). Mitigated: all three create paths now re-read via `getItemAfterCreate` (retry 0/350/700/1400ms) before declaring failure, so spurious cleanup no longer triggers. RESOLVED 2026-08-07: root cause was the service's ASYNC FileItem indexing — uploadFileV2 returns after S3 lands but the DB row (which DELETE consults) is written later, so a delete moments after upload dies with 'Could not find any entity of type FileItem' while reads (signed URLs) never notice. Fix: (1) createBinary uploads pass waitTillFileAddedInDb:true so the row exists before we proceed; (2) files.delete retries the FileItem-lag error across [0,600,1800]ms before surfacing it; 404 still means already-gone, other errors never retry. Mutation-checked both ways.
- [x] **GSX uploads were stored at unreadable keys (SDK prefix concatenation)** -- driven-release-pass catch (2026-08-05): `@or-sdk/files uploadFileV2` joins `prefix + fileName` by PLAIN CONCATENATION, so `lite-spaces/assets` stored objects at `lite-spaces/assets<name>` while every reader (previews, AI enricher, download) signed `lite-spaces/assets/<name>` -- permanent 404 on first-ever real read-back. Verified live end-to-end after fix: dialog upload -> thumbnail renders from signed GSX URL -> AI enrichment runs VISION modality (was degrading to hints on the 404). Orphaned mis-keyed objects deleted; broken asset node removed and re-created through the fixed path.

- [ ] **Remove the baked-in default OAGI / Neon graph from source.** `lite/neon/credentials.ts` exports `BAKED_IN_DEFAULT_GRAPH` containing the team's shared Aura URI / user / password / database plus the well-known Edison `/omnidata/neon2` endpoint. Remaining to fully close: seed every account's `lite-neon-config` server-side, then flip `LITE_NO_BAKED_GRAPH=1` for the public build and delete the constant. The pref order (account KV → baked) already prefers the account.
